# Create Requirement

Skill นี้ทำงานใน conversation หลัก (ไม่ใช่ subagent) เพราะต้องถามผู้ใช้กลับเมื่อไม่แน่ใจ ให้ทำตามขั้นตอนต่อไปนี้ตามลำดับ

โปรดอ่าน `CLAUDE.md` ที่ root ของ repo ก่อน (ถ้ายังไม่เคยอ่านใน session นี้) เพื่อเข้าใจโครงสร้าง `docs/` และ convention ของ vault

## ขั้นตอน

### 1. รับ requirement ดิบ

ถ้าผู้ใช้ยังไม่ได้ให้เนื้อหา requirement มาใน prompt ที่เรียก skill นี้ ให้ถามก่อนว่าต้องการสร้าง requirement เรื่องอะไร

### 2. ค้นหาเอกสารที่เกี่ยวข้อง/อาจซ้ำซ้อน

- ใช้ Grep/Glob ค้นใน `docs/01-requirements/01-spec/` หาเอกสารที่หัวข้อใกล้เคียงกับ requirement ที่ได้รับมา
- ถ้าผู้ใช้อ้างอิงเอกสารเดิมโดยตรง (เช่น พูดถึงไฟล์ใดไฟล์หนึ่ง หรือฟีเจอร์ที่เคยมี spec อยู่แล้ว) ให้เปิดอ่านเอกสารนั้นด้วย Read
- วิเคราะห์ว่า requirement ใหม่นี้ควร:
  - **สร้างเอกสารใหม่แยกต่างหาก** — ถ้าเป็นฟีเจอร์/ขอบเขตใหม่ที่ชัดเจน แม้จะเกี่ยวข้องกับของเดิม
  - **แก้ไข/เพิ่มเติมในเอกสารเดิม** — ถ้าเป็นรายละเอียดเพิ่มเติม การแก้ไข scope เล็กน้อย หรือ clarification ของ requirement เดิม
  - ถ้าไม่แน่ใจว่าเข้าเกณฑ์ไหน ให้ถามผู้ใช้ด้วย AskUserQuestion (ดูข้อ 3)

### 3. ถามเมื่อไม่แน่ใจ (บังคับ)

ทุกครั้งที่มีส่วนใดของ requirement ที่ไม่ชัดเจนพอจะเขียนเป็นเอกสารได้ — ไม่ว่าจะเป็นขอบเขต (scope), เงื่อนไขทางธุรกิจ, หรือว่าควรสร้างเอกสารใหม่หรือแก้เอกสารเดิม — ให้ใช้ **AskUserQuestion** ถามกลับ โดย:

- คำถามต้องมีตัวเลือกแนวทางให้เลือก **อย่างน้อย 3 แนวทาง** เสมอ (ไม่นับตัวเลือก "Other" ที่ระบบเพิ่มให้อัตโนมัติ)
- แต่ละตัวเลือกควรมีคำอธิบายสั้นๆ ว่าแนวทางนั้นหมายถึงอะไร/ผลลัพธ์เป็นอย่างไร
- ถามได้หลายคำถามพร้อมกันในการเรียกครั้งเดียวถ้าเป็นประเด็นที่แยกจากกันชัดเจน

อย่าเดาเอาเองในส่วนที่กระทบเนื้อหาสำคัญของ requirement (scope, business rule, การตัดสินใจสร้างเอกสารใหม่ vs แก้เอกสารเดิม) — ส่วนที่เป็นรายละเอียดปลีกย่อยจริงๆ (เช่นถ้อยคำ, การจัดหมวดหมู่ย่อย) ใช้ดุลยพินิจได้โดยไม่ต้องถาม

### 4. สรุปเนื้อหาที่จะเขียนลงเอกสาร

เมื่อข้อมูลครบถ้วนแล้ว ให้ร่างเนื้อหาเอกสารในใจ (หรือแบบร่างสั้นๆ) ให้ครอบคลุม: บริบท/ที่มา, feature requirements, user stories/use cases (ถ้ามี), business rules (ถ้ามี), scope (in/out) และเอกสารที่เกี่ยวข้องที่ควรลิงก์ถึง

กำหนด topic slug แบบสั้น เป็นภาษาอังกฤษ kebab-case (เช่น `user-login-otp`) สำหรับใช้ตั้งชื่อไฟล์

### 5. มอบหมายให้ subagent `requirement-writer` เขียนไฟล์จริง

เรียก Agent tool ด้วย `subagent_type: requirement-writer` (รันแบบ foreground คือ `run_in_background: false` เพราะต้องรอผลมารายงานผู้ใช้ต่อ) โดย prompt ต้องมีข้อมูลครบ ไม่ทิ้งให้ subagent ต้องตัดสินใจเอง:

- เนื้อหา requirement ฉบับสมบูรณ์ (พร้อมลงเอกสาร)
- topic slug
- action: `create_new` หรือ `update_existing` (พร้อม path เอกสารเดิมถ้าเป็นกรณีหลัง)
- path เอกสารอื่นที่เกี่ยวข้องซึ่งควรลิงก์ถึง (ถ้ามี)
- วันที่วันนี้ (YYYYMMDD) — ดึงจาก system context ของ conversation

subagent จะเป็นผู้จัดการ: ตั้งชื่อไฟล์พร้อม running number, เขียนเอกสารที่ `docs/01-requirements/01-spec/`, อัปเดต `docs/01-requirements/backlog.md`, และเขียน log ที่ `docs/05-log/{YYYYMMDD}-log.md`

### 6. รายงานผลให้ผู้ใช้

สรุปให้ผู้ใช้ทราบว่าไฟล์อะไรถูกสร้าง/แก้ไขบ้าง (พร้อม path) และข้อสันนิษฐานใดๆ ที่ subagent ระบุมา เพื่อให้ผู้ใช้ตรวจสอบ/แก้ไขได้ทัน
