# Create Architecture

Skill นี้ทำงานใน conversation หลัก (ไม่ใช่ subagent) เพราะต้องถามผู้ใช้กลับหลายจุด (การเลือก topic, การตัดสินใจเชิงแนวคิดที่ไม่ชัดเจน, การยืนยันแผน) ให้ทำตามขั้นตอนต่อไปนี้ตามลำดับ

โปรดอ่าน `CLAUDE.md` ที่ root ของ repo ก่อน (ถ้ายังไม่เคยอ่านใน session นี้) เพื่อเข้าใจโครงสร้าง `docs/` และ convention ของ vault

Skill นี้ทำงาน "ต่อยอด" จากเอกสารที่มีอยู่แล้วเท่านั้น (spec / feature list / user journey / prototype) — ไม่สร้าง requirement หรือ feature list/user journey ใหม่เอง ถ้ายังไม่มี ให้แนะนำผู้ใช้รัน `/create-requirement` และ/หรือ `/create-feature-journey` ก่อน

**หลักการสำคัญของเอกสาร architecture นี้**: ต้องเป็นระดับ **conceptual/high-level** เท่านั้น ห้ามผูกมัดกับ technical stack เฉพาะเจาะจง (ห้ามระบุชื่อภาษาโปรแกรม, framework, database engine, cloud provider ฯลฯ) ให้อธิบายด้วยคำเชิงบทบาทหน้าที่ (เช่น "ส่วนติดต่อผู้ใช้ฝั่งลูกค้า", "ที่เก็บข้อมูลออเดอร์", "บริการแจ้งเตือน") แทน การเลือกเทคโนโลยีจริงเป็นเรื่องของเอกสารอื่นในอนาคตภายใต้ `docs/02-design/02-technical/` (คนละไฟล์)

## ขั้นตอน

### 1. กำหนดขอบเขต (scope) ของ topic

เช็คว่าผู้ใช้ระบุ topic/feature เจาะจงมาในคำขอหรือไม่ (เช่น ชื่อไฟล์ spec, ชื่อฟีเจอร์)

- **ถ้าระบุเจาะจงมาแล้ว**: ใช้ Glob/Grep ยืนยันว่ามี spec ของ topic นั้นจริงใน `docs/01-requirements/01-spec/` ใช้เฉพาะ topic ที่ระบุ
- **ถ้าไม่ได้ระบุ**: ใช้ Glob ลิสต์ topic ทั้งหมดที่มี spec อยู่ใน `docs/01-requirements/01-spec/` แล้วถามผู้ใช้ด้วย AskUserQuestion (multiSelect ได้) ว่าต้องการทำ architecture สำหรับ topic ไหน อย่างน้อยควรมีตัวเลือกทำนอง:
  - **ทำทุก topic ที่มี spec ครบ** — ข้อดี: ได้ภาพรวม architecture ครบทั้งระบบในรอบเดียว มองเห็นจุดเชื่อมต่อระหว่างระบบ / ข้อเสีย: ใช้เวลานาน ตรวจสอบยากขึ้น
  - **เลือกเฉพาะบาง topic** (ให้ multiSelect รายชื่อ topic ที่เจอ) — ข้อดี: โฟกัสเฉพาะที่ต้องการ ตรวจสอบง่าย / ข้อเสีย: topic ที่เหลือยังไม่มี architecture doc
  - **ทำเฉพาะ topic ที่มี user journey แล้ว** — ข้อดี: มั่นใจว่า data flow ที่ร่างอ้างอิง user journey จริงได้ครบ ไม่ต้องเดา / ข้อเสีย: topic ที่ยังไม่มี user journey จะถูกข้าม

### 2. ตรวจสอบเอกสารต้นทางของแต่ละ topic ที่เลือก

สำหรับแต่ละ topic ที่จะทำ อ่าน/ตรวจสอบให้ครบทุกแหล่งต่อไปนี้ (ต้องอ่านให้ครบทุกอย่างที่มีจริง ห้ามข้ามเพราะรีบ):

1. `docs/01-requirements/01-spec/` — **บังคับต้องมี** ถ้าไม่มี ให้ข้าม topic นี้และแจ้งผู้ใช้ให้รัน `/create-requirement` ก่อน (ห้ามแต่ง spec เอง)
2. `docs/02-design/01-prototypes/{YYYYMMDD}-*-{topic-slug}-user-journey.md` — **บังคับต้องมี** เพราะ data flow ของ architecture ต้องอ้างอิงตามลำดับขั้นตอน/persona ในนี้ ถ้าไม่มี ให้ถามผู้ใช้ (ดูรายละเอียดด้านล่าง)
3. `docs/01-requirements/02-plan/` — feature list (แนะนำให้มี, ใช้ตรวจว่า component ที่ร่างครอบคลุมทุกฟีเจอร์)
4. `docs/02-design/01-prototypes/{topic-slug}/` — UI/UX prototype ถ้ามี (ใช้ช่วยยืนยัน touchpoint/หน้าจอที่ต้องมี component รองรับ, ไม่บังคับ)
5. `docs/01-requirements/backlog.md` — อ่านเพื่อรู้สถานะปัจจุบัน (ไม่บังคับต้องมี)

ถ้า topic ใดไม่มี user journey ให้ถามผู้ใช้ด้วย AskUserQuestion (อย่างน้อย 3 ตัวเลือก) เช่น:
- **หยุดรอ แนะนำให้รัน `/create-feature-journey` ก่อน** — ข้อดี: data flow จะอ้างอิงขั้นตอนจริงของผู้ใช้ได้ครบถ้วน / ข้อเสีย: ต้องรอ
- **ทำ architecture ต่อโดยอิงจาก spec อย่างเดียว** (ไม่มี user journey ประกอบ, ร่าง data flow แบบกว้างๆ จาก use case ใน spec แทน) — ข้อดี: ได้เห็นภาพรวมเร็ว / ข้อเสีย: data flow อาจไม่ตรงกับขั้นตอนจริงที่ผู้ใช้เจอ ต้องแก้ภายหลังเมื่อมี user journey
- **ข้าม topic นี้ไปก่อน ทำเฉพาะ topic อื่นที่พร้อม** — ข้อดี: ไม่เสียเวลารอ / ข้อเสีย: topic นี้ไม่มี architecture รอบนี้

### 3. เช็คว่าเป็นการเรียกซ้ำหรือไม่

สำหรับแต่ละ topic ใช้ Glob เช็ค `docs/02-design/02-technical/*-{topic-slug}-architecture.md` ว่ามีไฟล์ architecture ของ topic นี้อยู่แล้วหรือไม่

- **ถ้ายังไม่มี**: เป็น action `create_new`
- **ถ้ามีอยู่แล้ว**: เป็น action `update_existing` (แก้ไขไฟล์เดิมในที่เดิม ไม่สร้างไฟล์ใหม่ซ้ำ) ให้ Read ไฟล์เดิมมาดูก่อนว่ามี component/data flow อะไรอยู่แล้วบ้าง เพื่อไม่ให้ร่างซ้ำหรือขัดแย้งกับของเดิมโดยไม่ตั้งใจ ถ้าเนื้อหาที่จะเพิ่ม/แก้ขัดแย้งกับของเดิมอย่างมีนัยสำคัญ (เช่น requirement เปลี่ยนจนต้องรื้อโครงสร้าง component เดิม) ให้ถามผู้ใช้ด้วย AskUserQuestion ก่อนว่าต้องการแก้ไข/แทนที่ส่วนไหนบ้าง

### 4. อ่านเอกสารต้นทางแบบเต็ม

ใช้ Read อ่าน spec, feature list, user journey, prototype (เท่าที่มี) ของแต่ละ topic ที่จะทำให้ครบ

### 5. ร่างองค์ประกอบเชิงแนวคิด (Conceptual Components)

จาก spec + feature list ระบุ "องค์ประกอบ" ของระบบในระดับแนวคิด (เช่น ส่วนติดต่อผู้ใช้แต่ละ persona, บริการ/ความสามารถหลักที่ระบบต้องมี, ที่เก็บข้อมูลเชิงแนวคิดแต่ละประเภท, จุดเชื่อมต่อกับระบบภายนอกถ้ามีอ้างอิงใน spec) **ห้ามระบุชื่อเทคโนโลยีเฉพาะเจาะจงเด็ดขาด** ให้ใช้ชื่อเชิงบทบาทหน้าที่แทน ถ้า spec มีระบบอื่นที่เกี่ยวข้อง (เช่น topic นี้ใช้ข้อมูลจาก topic อื่น ตามที่ระบุใน backlog.md) ให้รวม touchpoint ไปยังระบบนั้นไว้ด้วย

### 6. ร่าง Data Flow ตาม User Journey

สำหรับแต่ละ persona ใน user journey ไล่ตามลำดับขั้นตอน (step) แล้วระบุว่าข้อมูลไหลผ่านองค์ประกอบใดบ้างในแต่ละขั้นตอน (เช่น "ขั้นตอน C3: ส่วนติดต่อผู้ใช้ฝั่งลูกค้า ↔ ที่เก็บข้อมูลเมนู") ร่างเป็น mermaid flowchart หรือ sequence diagram ที่อ้างอิง node id เดิมจาก user journey ให้ตรงกัน เพื่อให้ผู้อ่านโยงกลับไปดู user journey ได้ ระบุจุดที่เป็น pain point (ถ้ามีใน user journey) ว่ากระทบ component ไหนบ้าง

### 7. ร่างข้อมูลหลักที่ระบบต้องจัดการ (Key Conceptual Entities)

ระบุ "สิ่งที่ระบบต้องจดจำ" ในระดับแนวคิด (ไม่ใช่ schema จริง) เช่น ออเดอร์, รายการสินค้า, สถานะโต๊ะ พร้อมความสัมพันธ์คร่าวๆ ระหว่างกัน (ไม่ต้องมีชนิดข้อมูล/field ละเอียด)

### 8. ร่างข้อกังวลเชิงคุณภาพ (Non-functional Concerns) ระดับแนวคิด

ระบุประเด็นที่ควรพิจารณาในระดับแนวคิด อ้างอิงจาก business rules/scope ใน spec เช่น ความน่าเชื่อถือของการแจ้งเตือนแบบ real-time, ความเป็นส่วนตัวของข้อมูล (โยงกับ spec PDPA ถ้ามี), ความสามารถขยายระบบในอนาคตตาม scope ที่ยังไม่ทำ (out of scope) ในสเปค **ห้ามลงรายละเอียดเป็นวิธีแก้ทางเทคนิคเฉพาะเจาะจง** ให้คงเป็นระดับข้อกังวล/เป้าหมายเชิงคุณภาพ

### 9. ถามเมื่อไม่ชัดเจน (บังคับ)

ทุกครั้งที่มีส่วนใดของ component/data flow ที่ไม่ชัดเจนพอจะร่างได้ (เช่น ไม่รู้ว่าองค์ประกอบสองส่วนควรแยกหรือรวมกัน, ไม่แน่ใจว่า touchpoint ไปยังระบบภายนอกควรนับเป็นส่วนหนึ่งของ architecture นี้หรือไม่, ข้อกังวลเชิงคุณภาพขัดแย้งกับ scope ในสเปค) ให้ใช้ **AskUserQuestion** ถามกลับ โดยต้องมีตัวเลือกให้เลือก **อย่างน้อย 3 แนวทาง** เสมอ (ไม่นับ "Other" อัตโนมัติ) พร้อมข้อดี/ข้อเสียของแต่ละแนวทาง ส่วนรายละเอียดปลีกย่อยที่ไม่กระทบภาพรวม (เช่น ถ้อยคำอธิบาย) ใช้ดุลยพินิจได้โดยไม่ต้องถาม

### 10. เสนอแผนให้ผู้ใช้ยืนยันก่อนสร้างไฟล์จริง (บังคับทุกครั้ง)

ก่อนเรียก subagent เขียนไฟล์ ให้สรุปแผนเป็นข้อความให้ผู้ใช้อ่านทวนก่อนเสมอ ประกอบด้วย:

- topic ที่จะทำ และเอกสารต้นทางที่ใช้ต่อ topic (spec / feature list / user journey / prototype — ระบุว่ามีหรือขาดอะไร)
- action ต่อ topic: `create_new` หรือ `update_existing` (พร้อม path เดิมถ้าเป็นกรณีหลัง)
- รายชื่อ conceptual component ที่ร่างไว้ พร้อมคำอธิบายสั้นๆ ต่อ topic
- ภาพรวม data flow คร่าวๆ (กี่ persona, ครอบคลุมกี่ขั้นตอน)

จากนั้นถามผู้ใช้ด้วย **AskUserQuestion**: "ดำเนินการตามแผนนี้หรือไม่" พร้อมตัวเลือกอย่างน้อย 3 แบบ เช่น:
- **ดำเนินการตามแผนนี้เลย** — เริ่มสร้าง/แก้ไขไฟล์ตามที่สรุปไว้ทันที
- **ขอปรับแผนก่อน** — ให้ผู้ใช้บอกจุดที่อยากแก้ แล้ววนกลับไปปรับแผนใหม่ (ย้อนไปข้อ 5-10) ก่อนถามยืนยันอีกครั้ง
- **ยกเลิก** — ไม่ต้องสร้าง architecture รอบนี้

**ห้ามเรียก subagent เขียนไฟล์ก่อนได้รับการยืนยัน "ดำเนินการตามแผนนี้เลย" อย่างชัดเจน**

### 11. มอบหมายให้ subagent `architecture-writer` เขียนไฟล์จริง

เรียก Agent tool ด้วย `subagent_type: architecture-writer` (รันแบบ foreground คือ `run_in_background: false` เพราะต้องรอผลมารายงานผู้ใช้ต่อ) โดย prompt ต้องมีข้อมูลครบ ไม่ทิ้งให้ subagent ต้องตัดสินใจเนื้อหาเอง:

ต่อแต่ละ topic:
- topic slug และชื่อเรื่อง
- path ของ spec / feature list / user journey / prototype ต้นทาง (เฉพาะที่มีจริง)
- action: `create_new` หรือ `update_existing` (พร้อม path ของไฟล์เดิมถ้าเป็นกรณีหลัง)
- เนื้อหาฉบับสมบูรณ์: conceptual component ทั้งหมดพร้อมคำอธิบาย, data flow ต่อ persona (อ้างอิง node id จาก user journey), key conceptual entities, ข้อกังวลเชิงคุณภาพ — ตัดสินใจสุดท้ายแล้วจากข้อ 5-10 ไม่ใช่ให้ subagent ร่างเอง
- วันที่วันนี้ (YYYYMMDD) — ดึงจาก system context ของ conversation

subagent จะเป็นผู้จัดการ: หา running number และตั้งชื่อไฟล์ (กรณี `create_new`), เขียน/แก้ไขไฟล์ architecture พร้อมวาด mermaid diagram, เชื่อมลิงก์กลับไปยัง spec/feature-list/user-journey/prototype, อัปเดตสถานะใน `docs/01-requirements/backlog.md`, และเขียน log ที่ `docs/05-log/{YYYYMMDD}-log.md`

### 12. รายงานผลให้ผู้ใช้

สรุปให้ผู้ใช้ทราบว่าไฟล์อะไรถูกสร้าง/แก้ไขบ้าง (พร้อม path) และข้อสันนิษฐานใดๆ ที่ subagent ระบุมา เพื่อให้ผู้ใช้ตรวจสอบ/แก้ไขได้ทัน
